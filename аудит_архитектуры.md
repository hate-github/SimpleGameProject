# Архитектурный аудит прототипа «Дом на 6 соседей»

Дата: 6 сентября 2026. Объём: 14 900 строк Python, 952 ручки в balance.json, 870 уникальных ключей баланса читаются из кода строками.
Прочитано: README.md, ПЛАН.md (заголовки, введение, все «незакрытое» и «что может сломаться»), весь `house/` и все скрипты-линейки. Код не менялся.

Главный вывод в одну фразу: **логика домена в этом проекте богатая и хорошо продуманная, а структура — плоская: два модуля из девяти держат 45 % кода, границы между «мир / человек / что он видит / что он знает / что решает / что делает» существуют только в комментариях, а состояние живёт в строковых словарях. Расширять можно, но каждая новая механика уже стоит дороже предыдущей.**

Метод: Path B из patterns-and-refactoring — сначала запах, потом лекарство, и только затем вопрос, нужен ли паттерн.

## 2. Где orchestration

- `engine.Simulation.run → one_day → start_of_day / _morning / _day / _night / _upkeep` плюс хвост из семи вызовов `social.*`. Это настоящая оркестрация, и она читается.
- `actions.choose_and_do` — оркестратор одного хода (собрать → отфильтровать → softmax → выполнить).
- `conflict.run_siege` — оркестратор осады по стадиям (предупреждение → дверь → другой путь → прорыв → исход).
- `meeting.провести` — оркестратор собрания.
- `world.start_of_day` — оркестратор утра мира.
- `runner.many` — оркестратор прогонов.

Проблема не в том, что оркестраторов несколько, а в том, что **в `_morning`, `_night`, `_upkeep` и `run_siege` шаги не выделены в функции**: 208, 92, 182 и 357 строк последовательного кода, где каждый шаг — абзац с комментарием, а не имя.

## 3. Где смешаны decision и action execution

Проект декларирует разделение `gather` (оценка) / `execute` (исполнение), и для инициатора оно выдержано. Но **ответная сторона решает внутри исполнения**, и это не оформлено:

| Место | Что решается внутри `execute` или исполняющей функции |
|---|---|
| `execute["попросить"] → _ask` | `give = …` — хозяин решает, дать ли; `откроет` — открывать ли дверь; риск драки |
| `execute["переехать"]` | `yes = …` — 40 строк оценки хозяина «пустить ли», прямо в ветке |
| `execute["заказать"]` | `готов = …` — мастер решает брать ли заказ |
| `execute["отдать_на_ночь"]` | `возьмёт_ребёнка` (вынесено — хороший образец) |
| `execute["позвать"]` | `пойдёт_вдвоём` (вынесено — хороший образец) |
| `execute["обмен"] → _trade` | сосед пересчитывает выгоду по своему складу и может отказать |
| `run_siege` | `кричать`, откуп, уговор, побег, засада, сдаться, добить, занять, изгнать — девять решений жертвы и вожака вперемешку с перекладыванием банок |
| `conflict.steal` | `house_verdict`, «выйти со стволом», бежать/драться |
| `engine._decide_night` | вся ночная оценка (дежурить/красть/убить/обобрать) — в оркестраторе, а не рядом с `оценка_убийства` |
| `world._scripted_theft` | мир выбирает вора и жертву |
| `report.daily_chat` | выбор темы реплики и её социальные последствия |

Второе смешение: `execute` **пересчитывает** решение, которое `gather` уже принял (`что_заказать`, `чем_поделиться`, `find_deal`, `выбрать_место` вызываются дважды). Автор сознательно сделал «одно место на оценку и на исполнение», это правильно, — но результат оценки не передаётся в исполнение, а вычисляется заново, и между ними мир мог измениться. Для детерминизма это безопасно, для чтения — нет.

## 4. Где нарушены границы World / NPC / Perception / Knowledge / Decision / Action

**World ↔ NPC.** `NPC._h` — обратная ссылка на дом. Через неё `NPC.shelter`, `вес_черт`, `пунктик`, `плох`, `ребёнку_плохо`, `social.вес_слов`, `social.цена_денег` читают `House`. API модели непоследователен: `speed(b)` и `success(b)` берут баланс параметром, `вес_черт` — из `_h`. Это ровно то, что помешает перенести `model.py` в ресурсы Godot «одним файлом», как обещает README.

**Perception ↔ Knowledge ↔ Emotion.** Восприятие (`emit → _hear`, `smell`, `разглядел`) сразу пишет в знание (`est`, `вид`, `aware`, `memory`) **и** в чувства (`hate`, `panic`, `mood` внутри `smell`), **и** в журнал (`сводка`). Три слоя в одной функции. `memory` — список строк вида `д12:слышал:буржуйка:igor`, который `conflict.suspect` парсит подстроками (`"слышал" in m and other.id in m`). Это знание без типа.

**Knowledge ↔ Truth.** Граница «NPC не знает правды о соседе» проведена по договорённости, а не по типу: любой код решения может прочитать `t.stock`, `t.sick`, `t.injuries`, `t.skills`, `t.weapon`. Где-то это осознанно (`оценка_обобрать`: «здесь правда мира», `наблюдение`), где-то — нет: `поправимая_беда` читает `o.days_of(res)` соседей напрямую, `лечить` в `gather` использует `нужен_врач(t)` по правде, `consider_raid` — `t.dependents`, `t.skills`; `defenders_of` — `p.health` защитников. Автор сам ловил такие утечки («код читал `t.sick` прямо из правды мира») и чинил по одной. Пока нет объекта «что я вижу о соседе», они будут появляться снова.

**Decision ↔ Action.** Каждая ветвь `execute` — мини-транзакция на 4–6 подсистем: склад, отношения, знание, журнал, счётчики, `h.mods`. Порядок этих записей и есть поведение; переставить две строки — изменить эталон.

**Состояние без типа.** `h.mods` — мешок из 42 строковых ключей с четырьмя разными временами жизни: на день (`сделано`, `контакты`, `быт_сказано`), на несколько дней (`заказ_<id>`, `мастер_занят_<id>`, `дежурство`, `приговор_нужен`, `караулят`, `разрывы`), на всю жизнь (`календарь`, `погода_календарь`), буферы журнала (`сводка`, `запах_журнал`). Сброс на день делается вручную в `_morning`. Внешние скрипты пишут туда свои ключи (`дико`, `_пусто`). `npc.stats` — счётчики **и** состояние (`переехал_день`, `снёс_дров`, `раскрыт`, `под_подозрением`, `дорога_закрыта`, `отдых_день`). `h.stats` — метрики, бухгалтерия (`израсходовано_*`) **и** ворота поведения (`h.stats.get("краж")` в `что_подбросить`, `_scripted_theft`). Диагностика управляет симуляцией.

**Presentation ↔ Domain.** 193 вызова `journal.line/secret/note` разбросаны по домену (в `conflict` 76, в `actions` 45). Каждая правка правила — правка текста. `checks.Coverage` считает реплики, подменяя `actions.gform` и `Journal.chat`.

## 5. Запахи кода (по каталогу)

1. **Long Method** — `execute` 1232, `gather` 993, `run_siege` 357, `_outing` 253, `_morning` 208, `_upkeep` 182, `_ask` 153, `gossip` 131, `meeting._решение` 115, `consider_raid` 115.
2. **Large Class / God Module** — `actions.py`; `NPC` с ~60 полями; `House` с мешком `mods`.
3. **Switch Statements + Parallel tables** — `execute` на 49 `elif key ==`; действие описано в 12 таблицах по одному ключу: `COST`, `НОРМА`, `ТЕГИ`, `СУД`, `NOTABLE`, `СТРОЙКА`, `ПОСТРОЙКИ`, `ВИЗИТЫ`, `РАБОТА`, `ОБЫЧНОЕ`, `ВЫХОД_НА_ПЛОЩАДКУ`, `ПУНКТИК_КЛЮЧИ`/`ВЕСА_КЛЮЧИ` плюс `balance.часы_действий`, `лимит_в_день`, `лимит_на_пару_в_день`. Новое действие = Shotgun Surgery в 12–15 мест.
4. **Primitive Obsession / stringly-typed** — `h.mods`, `stats`, `memory`, травмы как строки (`"перелом ноги"` и `hurt("ноги")` по подстроке), `замысел` — dict, `дети` — list[dict], `body` — dict, `заказ` — dict, `обещал`/`врал` — list[dict], `ask_record` — dict с 13 ключами, часть динамических (`"нет_" + res`, `ключ_отказа`).
5. **Data Clumps** — на каждую пару людей шесть словарей `trust/hate/aware/страх/близость/счёты` + `est`, `вид`, `asking`, `не_верю`, `favors`, `дал`, `не_прощу`, `не_жилец`, `не_вышли`. Отношение как понятие есть, как тип — нет. Тройка `(h, npc, b)` кочует по сотне сигнатур.
6. **Duplicated Code** — смерть выставляется руками в **7 местах** (`fight` ×2, `убить_соседа`, `run_siege` «добить», `world._scripted_cold_death`, `world.угар`, `on_death`); `alive and not exiled` — 63 раза; `(npc.values or {}).get("ценит") or ()` — 8 раз; `flat_temp(…, burning=своя_топится(…), powered=h.power_on)` — 6 раз; переписывание четырёх падежей ребёнка — в 3 местах; цикл «take_household по crew и слить moved» — 5 раз в `run_siege`.
7. **Magic Numbers** — при 952 ручках в данных в формулах остались сотни литералов (`/ 25.0`, `hate=25 + 15 * …`, `trust=-4.0`, `0.35 + 0.4 * …`). Нет правила, что идёт в balance, а что нет.
8. **Feature Envy** — `social.выгода_соседства` зовёт `conflict.household` и `h.flat_temp`; `engine._morning` исполняет заказ, читая `actions.УСЛУГИ`; `engine._upkeep` крутит детские словари; `world.start_of_day` читает `actions.МЕСТА`.
9. **Divergent Change** — `social.py` (пять причин меняться), `engine.py` (физиология, ночь, услуги, обнаружения, сборка, валидация).
10. **Inappropriate Intimacy** — пять внешних скриптов и `checks.Coverage` **подменяют функции модулей** (`actions.execute` ×4, `actions._outing` ×3, `actions.gather`, `conflict.run_siege`, `conflict.defenders_of`, `social.adjust`) и пишут в `h.mods` / `npc.stats` свои ключи.
11. **Flag Arguments** — `известно`, `вслух`, `завтра`, `выгоняют`, `quiet`; `emit(text_for=None)` не используется нигде.
12. **Long Parameter List** — `defenders_of(h, target, crew_ids, предупреждён, поднял, крик)`, `judge(h, actor, tag, hate, trust, witnesses, участники)`.
13. **Temporary Field / lifecycle by convention** — `time_left`, `away`, `burning`, `tonight` сбрасываются в `_morning`; забыть сброс — баг, который автор уже ловил («без сброса в поле висело вчерашнее решение»).
14. **Lazy imports как симптом циклов** — 60 импортов внутри функций.
15. **Dead / vestigial** — `NPC.dependents_only_child` заглушка, `EmptyFlat` алиас, `NPC.door_strength` дублирует `Flat.door_strength`, `util.lerp` не используется, `emit.text_for`.
16. **Comments carry the structure** — это не запах в обычном смысле: комментарии здесь — журнал дизайна и главный актив проекта. Но они компенсируют отсутствие имён: `_morning` — восемь абзацев с комментариями вместо восьми функций. При рефакторинге комментарии обязаны переезжать вместе с кодом, иначе потеряется то, ради чего проект писался.

## 7. Coupling и circular dependencies

**Объявленный граф импортов** (верхний уровень) ацикличен: `util → model → social → conflict → meeting`, `world → util`, `замысел → util`, `actions → social, conflict, meeting, world, замысел`, `engine → всё`.

**Реальный граф** (с учётом 60 ленивых импортов внутри функций) содержит циклы:

- `actions ↔ social` — social читает `actions.НОРМА` (`переступил`).
- `actions ↔ conflict` — conflict читает `actions.своя_мерка` (`recruit`).
- `actions ↔ world` — world читает `actions.МЕСТА` (`start_of_day`, `условие_верно`); actions зовёт world.
- `social ↔ conflict` — social зовёт `conflict.household`, `conflict.reveal_taboo`.
- `world → social, conflict` при том, что `conflict → social`, `actions → world`.
- `engine → checks → actions` при `engine → actions`.
- `замысел → social` при `actions → замысел`.

Корень почти всех циклов — **константы, живущие в `actions.py`**: `НОРМА`, `ТЕГИ`, `МЕСТА`, `КЛАДОВЫЕ_ВИДЫ`, `COST`, `ЦЕННОСТИ`, `ПУНКТИК_КЛЮЧИ`, `ВЕСА_КЛЮЧИ`; и **функции характера** `своя_мерка`, `мерка_поступка`, `norm_gate`, которые нужны conflict и meeting. Второй корень — понятие «где человек и с кем» размазано на четыре функции в трёх модулях: `House.where`, `House.хозяин_жилья`, `social.место`, `social.под_одной_крышей`, `conflict.household`.

Другие связи, которые стоит назвать:

- `NPC._h` — модель зависит от дома (см. §4).
- `h.B["…"]` — 870 уникальных строковых ключей; опечатка обнаруживается только `KeyError` в момент выполнения ветки, которая может не выполняться десятки прогонов. `validate_data` проверяет данные против кода, но не код против данных.
- `report.daily_chat → social` — презентация мутирует домен.
- Скрипты-линейки и `Coverage` привязаны к **именам функций** через monkeypatching. Любое переименование `execute`, `_outing`, `run_siege`, `defenders_of`, `adjust` ломает пять скриптов молча.
- **Детерминизм как связность**: порядок вызовов `rng` — часть поведения. Любая перестановка двух независимых шагов меняет прогон. Это не запах, это свойство симуляции, но оно превращает каждый рефакторинг в поведенческое изменение с точки зрения эталона.

## 8. Где особенно опасно продолжать расширять

1. **`gather` / `execute` + 12 таблиц.** Каждое новое действие — правка двух функций по тысяче строк, дюжины таблиц и `balance.json`. Уже сейчас `execute` — 49 ветвей, часть из которых пересчитывает решение. Следующие пять действий ГДД (ловушки, камера, расписание) удвоят стоимость каждого.
2. **`run_siege`.** Одиннадцать выходов, у каждого свой набор `обидели / adjust / _house_learns / bump`. Забытый вызов в новом выходе — молчаливый баг, который поймает только замер. ГДД 16 ещё не закрыт (ловушки, уровни 3–4).
3. **Пути смерти.** Семь мест выставляют `alive/health/cause/died_day` руками, у `on_death` пять параметров и три способа вычислить свидетелей. Новый вид смерти (ловушка, пожар) почти наверняка пропустит либо `on_death`, либо `ledger`.
4. **`h.mods` как хранилище состояния.** Каждая новая многодневная механика добавляет строковый ключ с неявным временем жизни. Внешние скрипты уже пишут туда. Это первое, что сломается при сериализации/сохранении, которое понадобится в Godot.
5. **Ребёнок как dict.** Три модуля, три места переписывания падежей. Второй тип иждивенца или второй ребёнок с именем — переписывание.
6. **`memory` как строки.** Новый вид сигнала = новая позиция в 4-кортеже `NOISE_MEANING` и новый формат строки, который кто-то потом будет парсить подстрокой.
7. **Игрок как седьмой жилец** (README, ГДД 13). Сейчас нет шва, куда воткнуть чужое решение: день — `softmax` внутри `choose_and_do`; ночь — `_decide_night` внутри оркестратора; в осаде решения жертвы (`кричать`, откуп, побег, сдаться) вычисляются с `rng` внутри `run_siege`; хозяин в `_ask`/`переехать`/`заказать` решает внутри `execute`. Это самая важная будущая ось изменения, и под неё архитектура не готова.
8. **Перенос в Godot «по одному файлу»** невозможен при текущих циклах, `_h` и `h.mods`. `model.py` в ресурсы — да; `actions.py` в «скрипт поведения NPC» — нет, потому что он же исполняет мутации мира, отношений и журнала.

## Список проблем по приоритету

1. **Нет шва для чужого решения** (игрок, тест, сценарий) — блокирует главную цель ГДД и порт. Причина: `gather`/`_decide_night`/`run_siege`/`_ask` принимают решение и тут же исполняют.
2. **`actions.py` как God Module** с 12 параллельными таблицами и двумя функциями по 1000 строк — главная стоимость каждого расширения.
3. **Реальные циклы импортов** через константы и функции характера в `actions.py`; `NPC._h`.
4. **Состояние без типа**: `h.mods`, `stats` как флаги, `memory` как строки, ребёнок/замысел/заказ/тело как dict.
5. **Семь ручных путей смерти** и дублирование в `run_siege`.
6. **`engine.py` держит физиологию, ночь, услуги, обнаружения, сборку, валидацию** вместо оркестрации.
7. **Граница «знание ≠ правда» только по договорённости** — утечки правды в решения будут появляться снова.
8. **Презентация в домене**: 193 вызова журнала, `daily_chat` в `report.py`.
9. **Monkeypatching** в `checks.Coverage` и пяти скриптах вместо хуков.
10. **Смешение диагностики и поведения** (`h.stats` как ворота).
11. Магические числа в формулах при 952 ручках; неполная валидация ключей `h.B`.

## Какие паттерны действительно оправданы

Проверено через YAGNI-ворота (три варианта сегодня, названный источник, окупаемость, наивная версия хуже).

1. **Таблица-диспетчер действий** (Command в самом лёгком виде: запись + две функции `оценить`/`исполнить`, зарегистрированные в dict). Вариантов — 49 сегодня, источник — ГДД 12.5 и 15, наивная версия — те самые 2200 строк. Классы не нужны: dict функций — идиома Python.
2. **Strategy для принятия решения** (`Решающий` с `день(варианты) -> выбор`, `ночь(варианты)`, `в_осаде(ситуация)`). Три варианта: softmax-NPC, человек (ГДД 13, README), детерминированный/скриптовый для тестов и сценариев. Выбирается на каждого жильца при сборке. Это единственный паттерн, ради которого стоит менять сигнатуры: он делает игрока седьмым жильцом без переписывания правил. Вводить **после** того, как `gather`/`execute` и ночь станут «список оценённых вариантов → выбор → исполнение» в чистом виде.
3. **Очередь отложенных событий** (Event Queue в минимальном виде — типизированный список на `House`, разбираемый утром). Пять случаев уже есть (`пропажи`, `вскрытые_кладовые`, `подброшено`, `не_простил`, `сводка`), все следуют одному узору.
4. **Observer как список хуков** для измерений. Пять клиентов уже подменяют одни и те же четыре функции. Это не «событийная шина», а `h.hooks.on_execute.append(fn)`.
5. **Value Object для «взгляда на соседа»** (`Взгляд(сыт, цел, тепло, хворь, день)` + `Сведения(est, aware)`) — типизирует границу знание/правда: решение получает `npc.видит(t)` и не имеет `t` в руках. Это Extract Class на уже существующих `вид`/`est`, а не новая механика. Отложить до момента, когда модули станут меньше; но именно он закрывает п. 7 приоритетов.
6. **Builder/фабрика** только как функция `build_house(data)` — не класс.

## Какие паттерны НЕ следует вводить

- **ECS** (entity-component-system) — соблазн при мысли о Godot. Шесть сущностей, правила плотные, а не сущности массовые; ECS размажет формулы по системам и убьёт читаемость комментариев-объяснений.
- **Event Bus / Event Sourcing для всех `adjust`** — детерминизм и явный порядок вызовов здесь ценность; шина сделает порядок неявным и сломает эталон при первом же изменении подписчиков. Явные `witnesses=` в `judge` — это дизайнерское решение, а не недоработка.
- **Иерархия классов действий** (`AbstractAction` → 49 подклассов) — разнесёт 2200 строк по 49 файлам без выигрыша; dict функций и модули по предметной области (`быт`, `стройка`, `соседи`, `улица`, `кладовые`, `интрига`) дают то же дешевле.
- **Behavior Tree / GOAP** — оценка полезности плюс `замысел` как долгий слой уже делают то, ради чего вводят GOAP. Замена сотрёт три месяца настройки.
- **State pattern для жив/изгнан/ушёл** — три булева поля; достаточно enum и метода `здесь()`.
- **Repository / Unit of Work / DDD-агрегаты** — персистентности нет.
- **DI-контейнер, Singleton для `House`** — `h` передаётся явно, и это правильно; сохранить.
- **Observer для распространения отношений** (автоматическое «все узнали») — противоречит ГДД 13: кто увидел, тот и знает.

## Рекомендуемый порядок рефакторинга

**Шаг 0 — страховочная сеть (обязательно первым).** Эталон (`data/эталон.json`) сейчас — четыре отпечатка; расширить до 20–30 зёрен и хранить отпечаток **по дням**, чтобы регрессия локализовалась днём, а не «где-то в прогоне». Зафиксировать правило: шаг рефакторинга = одна правка, `check.py` зелёный без `--золотой`; любая перестановка вызовов `rng` — отдельный коммит с осознанным `--золотой` и записью в ПЛАН. Добавить обратную проверку ключей `h.B`.

**Шаг 1 — чистые переносы, ноль семантики.** Константы из `actions.py` в `catalog.py` / `street.py` / `character.py`; четыре функции «где он» в `House`; `daily_chat` в `chat.py`; `validate_data`+`load_json` в `schema.py`; `_build` в `assembly.py`. Убирает почти все ленивые импорты и циклы. Комментарии переезжают вместе с кодом.

**Шаг 2 — распил `execute` и `gather`.** По одной ветке за шаг: `elif key == "X": …` → `def _исполнить_X(h, npc, target, spent)`, регистрация в dict, эпилог общий. Затем разделы `gather` → функции с явной корзиной. Порядок вызовов внутри ветки не меняется — эталон держится.

**Шаг 3 — одна запись `Действие` вместо 12 таблиц** + проверка полноты при импорте. После шага 2 это механическая правка.

**Шаг 4 — вынос из `engine.py`** по таблице §6: `physiology`, `child`, `night`, `services`, `discoveries`, `household`. `_morning` и `_upkeep` превращаются в последовательность именованных вызовов.

**Шаг 5 — единый путь смерти и общие guard-функции** (`умер`, `здесь()`, `ценит()`); консолидация дублей в `run_siege`.

**Шаг 6 — типизированное состояние.** `h.mods` → `Сутки`/`Ожидает`/`Календарь` + именованные поля; `stats`-флаги → поля NPC; `Ребёнок`, `Замысел`, `Заказ`, `Тело`, `Обещание` — dataclass'ы. Много мест, поэтому только после того, как модули стали маленькими.

**Шаг 7 — хуки для измерений** вместо monkeypatching; перевести `Coverage`, `замер`, `поводы`, `своё`, `снаружи`, `вдвоём`.

**Шаг 8 — шов решения (`Решающий`) и `Взгляд` как тип.** Это единственные шаги, где меняется форма API, и они дают игрока-жильца и честную границу знание/правда. Делать последними, на чистой основе.

**Не делать вовсе на этом этапе:** объект «Отношение» вместо шести словарей (сотни мест доступа, выигрыш меньше цены), ECS, шина событий.

## Две оговорки, которые важнее любого шага

1. **Комментарии — это документация проекта.** ПЛАН.md и README ссылаются на них, замеры объясняются ими. Любой инструмент или подход, который теряет комментарий при переносе функции, недопустим. Рефакторинг здесь — переезд абзацев, а не переписывание.
2. **Эталонный тест — единственная защита, и он хрупок в обе стороны.** Он поймает любую перестановку вызовов `rng`, но не отличит «сломал» от «переставил два независимых шага». Поэтому шаги 1–5 должны быть настолько мелкими, чтобы падение эталона всегда объяснялось одной правкой.

# Дом.Годот — третья сборка, пока пустая

Проект движка. Заводится на **этапе 3** переезда (`docs/ПЕРЕЕЗД.md`), когда
ядро уже сошлось с эталоном и в консоли сыграны тридцать дней. Пустой она
стоит здесь не для порядка, а чтобы направление зависимостей было записано
до того, как появится первый узел.

## Направление зависимостей

```
Сцена Godot → Вид/Адаптер → API симуляции → Дом.Ядро
```

Только вниз. Обратной стрелки нет:

- `Дом.Ядро` — ни одного `using Godot`. Это не пожелание, а проверка:
  `Дом.Консоль проверить` считает вхождения и краснеет на первом же.
- `Дом.Консоль` — прогон, проверки и игра руками. Зависит от ядра.
- `Дом.Годот` — сцены, узлы, ввод, звук, интерфейс. Зависит от ядра
  и ни от чего больше; консоль о нём тоже не знает.

Простая проверка границы: **сутки должны считаться из консоли, без сцены
и без рендера.** Если для этого понадобится `SceneTree` — граница нарушена.

## Что здесь будет и чего здесь не будет

Будет: план подъезда, журнал дня, экран вопроса, своё состояние, телефон;
`Resource` — для моделей, материалов, звуков, шрифтов и привязки
«жилец → внешность».

Не будет: нужд, памяти, знания, отношений и решений. Ни один узел за них
не отвечает. Если ради интерфейса захочется положить решение в `Node` —
значит, не хватает адаптера, а не архитектуры.

Отдельно: **баланс, жильцы, события и реплики остаются JSON** (`data/*.json`)
и читаются ядром напрямую. В `.tres` их не переводить — это убьёт
двустороннюю проверку ручек и рассыплет настройку по редактору.

## Тик

Симуляция считает сутки, а не кадры. Игрок нажал «дальше» → адаптер зовёт
сутки (или очередной ход) → получил поток событий → проиграл его
в интерфейсе. Никакого `_Process(delta)` у каждого жильца.

Подробности — навык `godot-boundary`.
